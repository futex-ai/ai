# Empty instructions produce an invalid array

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Small. **Confidence:** Medium. **Harder later:** Yes.
- **Kind:** Needs decision.
- **Added:** 2026-11-26, from branch `calummoore/adding-openai-decisions-api-9ler`, review round 1, finding 4.
- **Location:** `crates/ai-models-openai/src/openai/decisions/input.rs:76`, `crates/ai-models-typesafe/src/typesafe/request.rs:136`, `crates/ai-interface/src/judgment/request.rs:23`, `crates/ai-models-openai/src/openai/decisions/_tests_/request_tests.rs:47`, `docs/protocol/openai-judgment-provider.md:180`, `docs/protocol/judgment-boundary.md` (section "Local Validation")
- **Reason:** The recommended option adds a stricter validation and a new question problem to the shared judgment contract, and the user decides each new rejection.

- **Terms:**
  - **Instructions:** the `JudgmentContent` of each judgment question, an ordered list of text, JSON, and image parts. `docs/protocol/judgment-boundary.md` defines it.
  - **Local validation:** the method `JudgmentRequest::validate` in `crates/ai-interface/src/judgment/request.rs`. The mock and every judgment adapter call it before transport.
  - **Question problem:** a variant of `JudgmentQuestionProblem`, such as `NoOptions` or `TooFewLevels`. Local validation returns it in an `InvalidQuestion` error.
  - **Decisions:** the OpenAI judgment endpoint `POST /v1/decisions`. `OpenAiJudgmentModel` in `crates/ai-models-openai/src/openai/decisions/` calls it.
- **Background:**
  - Local validation checks the question id, the options of a choice, and the levels of a score. It does not check instructions, so a question with zero instruction parts passes.
  - `docs/protocol/openai-judgment-provider.md:180` says that one text part becomes a string and that other instructions become an array of parts. So zero parts become `instructions: []`, in `crates/ai-models-openai/src/openai/decisions/input.rs:76`.
  - On 2026-11-26, a loopback capture showed `instructions: []` on the Decisions wire.
  - The review of 2026-11-26 states that Decisions accepts an empty string for instructions and requires at least one part in the array form. Nobody sent such a request to OpenAI.
  - One question with zero parts invalidates the whole Decisions request, so no question of the call gets an answer.
  - A caller can work around it with one empty text part, which the adapter sends as the empty string.
  - The TypeSafe adapter also sends zero parts as `instructions: []`, in `crates/ai-models-typesafe/src/typesafe/request.rs:136`. Nobody checked whether TypeSafe rejects it.
  - The mock applies the same local validation and answers every question, also a question with zero instruction parts.
  - The request tests in `crates/ai-models-openai/src/openai/decisions/_tests_/request_tests.rs` use one text part or a nonempty array, so they miss this case.
- **Problem:** Local validation accepts a question with zero instruction parts. The Decisions and TypeSafe adapters then send `instructions: []`, and Decisions rejects that form.
- **Impact if no action:** One such question makes the provider reject the whole request, so the call returns no judgments. The error does not name the question.
- **Root question:** What does a question with no instruction parts mean at the judgment boundary, so that no adapter sends a request that its provider rejects?
- **Options:**
  - **A.** Keep the provider rejection, and document the workaround of one empty text part. Effort: Small.
  - **B.** The Decisions adapter sends an empty string for zero instruction parts. Update the request mapping of `docs/protocol/openai-judgment-provider.md` and add a wire regression. This makes an exception to the rule that instructions other than one text part become an array. TypeSafe keeps `instructions: []`. Effort: Small.
  - **C.** Give Decisions an instruction wire type whose array form requires a first part, and give the empty case the string form. Effort: Medium.
  - **D.** Shared local validation requires at least one instruction part, with a new `NoInstructions` question problem. One blank text part stays valid. Every adapter and the mock reject zero parts before transport. Update `docs/protocol/judgment-boundary.md`. Effort: Small.
  - **E.** Shared local validation rejects blank instructions, with a `BlankInstructions` question problem. It uses the emptiness rule of the input: no parts, or only whitespace text and empty JSON. This is stricter than Decisions, which accepts an empty string. Effort: Small.
  - **F.** The shared type of instructions cannot hold zero parts, for example a first part and a list of the other parts. This changes a public `ai-interface` type, so every caller crate changes with it. Effort: Medium.
- **Left out:** A rejection in the Decisions adapter only: TypeSafe sends the same empty array, and D covers every adapter with the same effort. A property test over the question forms: F prevents the case by type instead of detecting it.
- **Wider fix:** F. A type that cannot hold zero parts prevents the case for every adapter and every new question mapping. The first review pass named C.
- **Previous examples:** Local validation already rejects a choice without options, with `NoOptions`, and a score with fewer than two levels, with `TooFewLevels`. `plans/follow-ups/user-text-array-form.md` records another choice between the string form and the array form on provider wires.
- **Related:** `plans/follow-ups/judgment-tool-result-without-call.md`: the same cause and the same code. Shared validation accepts a form that the Decisions wire rejects, so one answer on where such a rule lives fits both items.
- **Recommendation:** D. It rejects the empty case before transport for every adapter and the mock, beside `NoOptions` and `TooFewLevels`, and it keeps one blank text part valid. The first review pass recommended B. F best protects new question mappings.
- **Action:** ask the user, because D adds a stricter validation to the shared judgment contract, and only the user adds a rejection.
